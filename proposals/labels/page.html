GoFish API proposal

Labels for Points, Lines and Areas

Proposal, not implemented; syntax awaiting sign-off
Revised after review round 1

Place.along now covers open paths and region boundaries, with a side option, and today's position strings are along on a rect's parts. Place.around reads screen directions, and one geometry query, Outline, serves both. See section 05, Sides and boundaries.

Summary

Keep one .label(). Give its position option a strategy family, Place, whose members read the labeled mark's geometry (a point, a path, or a region) and propose candidate spots. One shared step then picks, for each label, the first spot that is free of other labels and of anything listed in avoiding.

Recommendation

Approach A: .label(accessor, { position: Place.end(), avoiding }). Each Place member is defined by a rewrite into today's elaborated shape (layer([ref(target), text]) plus a placement), so the core grows by one geometry query (outline, #974's boundary extended to open paths and named parts) and one search step, the same kind of step as scatter's overlap. The runner-up is a public label(...) tier for .layer()/.relate() (Approach C), which A desugars into anyway.

Taxonomy answer

A label is not a fifth kind of construct. It is the "mixed row" of the operand-kind table in Operators over placed nodes: it reads a placed operand (the target) and places a fresh one (the text). Marks, relational marks, constraints and labels are clusters of three per-operand facts, plus one fact about how coordinates get written.

01Where labels fit

Target
The mark a label describes. It is already placed when the label is placed.
Label
A fresh mark, usually text, placed relative to the target.
Geometry kind
What shape the target offers for labeling: a point (a dot, or any mark read as its box or enclosing circle), a path (an open curve with a start, an end and a direction: a line, an edge, an arrow), or a region (a closed area: an area band, a polygon, a treemap cell). Cartography uses the same three: point, line and polygon features.
Candidate
One possible spot for a label, in priority order.
Placement strategy
A rule that turns a target's geometry into candidates. These form the Place family.
Obstacle
Something a label must not cover: other labels, the targets, or marks named in avoiding.
Chooser
The shared step that takes each label's candidates in order and keeps the first one that does not hit an obstacle. A label with no free candidate is hidden. This is the greedy first-fit rule of Imhof's cartographic placement, Mapbox's text-variable-anchor, CSS position-try-fallbacks, and Vega's label transform.

Josh asked whether a label is a new kind of thing beside marks, relational marks, relations and constraints, or whether those categories come from something more basic. The internals essay Operators over placed nodes (#707) already answers half of this. Its table indexes arrangements by operand kind:

operands today's name places whom reports upward
all fresh operator (spread) all children the children
mixed refs + fresh (unnamed idiom) = the label fresh children only fresh only
all refs, no ink constraint (align) pins or moves refs nothing
all refs + drawn ink connector (line) nothing, reads the drawn ink

The unnamed row is the label. BarWithLabels writes it by hand as spread({ dir: "y" }, [d[0], text(...)]), and #766 made .label() elaborate into exactly that shape: Layer[ref(target), Text] plus align and distribute constraints. Josh's labelLayout([ref(labeledMark), labelText]) is the same picture.

  • ref(target): placed operand, read only. Its geometry (here a point) produces the candidates.
  • candidates: Place.around()'s eight compass spots, upper right first (the order drawn is illustrative).
  • obstacle: read, neither placed nor drawn by the label. Spot 1 crosses it.
  • fresh text: the only thing the label places. The chooser keeps spot 2, the first free one.

The categories fall out of three facts about each operand, plus one about how positions are written:

  1. Binding. Does the construct place this operand (fresh), or only read it (placed, a ref)?
  2. Ink. Does the construct draw, and if so is the ink's shape its own (text has an intrinsic size) or derived from the operands (a line's path, an enclosure's outline)?
  3. Reads. Which geometry does it read from placed operands: a box, a point, a path, a region outline?
  4. Writer. Are positions written by equations (align and distribute, the difference constraints the solver handles) or by a search over candidates (scatter's overlap: Overlap.separate(), the choose operator from #486, and labels that avoid things)?
construct operands ink reads writer
mark (rect) none own none parent
operator (spread) fresh none boxes equations
constraint (align) fresh or placed none boxes equations
relational mark (line, ribbon, enclose) placed derived boxes (paths later) none (nothing moves)
label, fixed spot (today) placed target fresh text own box equations
label, with candidates placed target fresh text placed obstacles own point path region search
enclose({ shape: Shape.blob({ avoiding }) }) placed members placed obstacles derived discs segments boxes none

blue marks the answers this proposal adds for labels. dashed means the fact does not apply.

So the difference Josh felt between a label and the relational marks is fact 2. A relational mark's ink is computed from its operands (a line is the path through them), while a label's ink has its own shape and only its position comes from the target. Avoidance adds a third operand role, the obstacle, which is read but neither placed nor drawn. enclose's avoiding in #1152 already has this role. A label with several candidates also changes fact 4: "pick a spot that misses everything" is not a difference constraint, so it is a search step that runs after the solve that places its targets, as overlap does today (constraints/overlap.ts).

The categories are clusters in this four-fact space, not a list to extend. That is why they "are not exactly perfectly orthogonal": a relational mark and a label differ in one fact, and a constraint and an operator differ in one fact. Nothing in this proposal needs a fifth category. It needs two more answers to fact 3 (path and region) and one more answer to fact 4 (search) for labels.

Three things recur

  1. The target's geometry decides how candidates are made, and the collision test is shared. Vega's thesis says the chart types "only differ in (1) the marks to be avoided and (2) the candidate positions".
  2. The strategy is a family, often with combinators.
  3. The avoid set is named, by reference or by scope, and labels avoid each other by default.

03Today vs proposed

What exists today:

  • .label(accessor, options) on marks and on operators (#750, #766). Options: position ("center", "outset", "outset-top", "inset-top-start", …), offset, fontSize, color, rotate, fontFamily, fontWeight, fontStyle. It elaborates into Layer[content, ref(target), Text] with align and distribute constraints, at the target's parent, so labels never push marks apart. Only boxes are read.
  • Relational marks (line, ribbon) accept .label() but read the connector's box, so a line label lands at the box's top edge, not on the line.
  • Geometry. node.geometry() exists (#968) with one query, enclosingCircle. The line and area paths exist in connect's renderData.paths, and a polygon's ring exists in a closure, but nothing exposes them. #974 proposes the boundary query and names labels as one of its two first users.
  • Avoidance precedent. #1152 (draft) gives Shape.blob an avoiding option that takes a list of refs or one selectAll(...), sent over the wire as NodeSelectionIR, and reads each obstacle through a private reader (circle → disc, line → segments, else box) that it calls "the first private step toward #974".
  • Search precedent. scatter's overlap: Overlap.separate() is a placement step after the constraint solve that reads geometry() and moves children (#969).

How the proposed pictures were made: the real chart is drawn by GoFish; a prototype (packages/gofish-graphics/stories/_proposals/labels/place.ts) reads the drawn geometry from the SVG, runs the strategy and the chooser, and adds the labels on top. Approximations are in that folder's NOTES.md.

04The Place family

Each member turns one geometry kind into ordered candidates. A member that needs geometry the target does not have is a loud error naming the missing capability, for example Place.interior needs a closed outline; line has an open one.

Revised after review round 1 (section 05): along now covers both open paths and region boundaries, with a side option; today's strings are shorthand for along on a rect's parts.

member reads candidates precedent
Place.along({ at, side, orient, offset }) outline an open path or a region's boundary the spot at at, then nearby spots along the outline; at each, the sides listed in side TikZ pos/sloped/auto, geomtextpath hjust/vjust, QGIS Parallel / Curved / Using Perimeter, Mapbox symbol-placement: line
"outset-top", "inset-top-start", … (today's strings) a rect's parts one: "outset-top" is Place.along({ at: "top", side: "outset" }) today; Vega anchors
Place.around({ candidates? }) outline by screen direction the outline's extreme point in each of 8 compass directions, upper right first, outside; or a given list Imhof, Christensen et al., Vega-Lite defaults, CSS fallbacks
Place.start(), Place.end() open path past the path's first or last point, horizontal, sliding along y to clear neighbors directlabels first.qp/last.qp, Plot selectLast, Vega lineAnchor
Place.interior() region the spot where the label's own box can grow largest; hide if it does not fit d3-area-label, Vega reduced-search; not polylabel

Defaults come from the geometry kind, so the meaning lives on the target's type: box marks keep "outset", dot marks get Place.around(), paths get Place.end(), regions get Place.interior(). Custom strategies use #1101's function hatch: a function from geometry to candidates.

05Sides of a path, and a path that is a boundary

New in review round 1

Josh asked: what about labels above or below a path, and what about a path that is the boundary of a shape? Both fit along, and the second one folds today's box vocabulary into it.

Sides of an open path

Precedent has two frames for "side". The screen frame is TikZ above/below and QGIS "above line / below line". The path's own frame is TikZ auto=left|right and QGIS "line orientation dependent": left or right of the direction of travel. side takes both, and "on": 

line({ stroke: "symbol" }).label("symbol", {
  position: Place.along({ at: 0.6, side: "above", orient: "sloped" }),
})
arrow({}, [ref(A), ref(B)]).label("submit", {
  position: Place.along({ at: 0.5, side: "left", orient: "sloped" }),
})

The two frames are not redundant. On a diagram the path frame is the one that works: with side: "left" every label of a clockwise cycle lands outside it, and the two labels of a pair of opposite edges separate. With side: "above", the labels on the two vertical edges are hidden, because a vertical stretch has no "above". That is inherent to the screen frame, not a prototype bug: above is partial, defined only where the path is not near vertical, and it flips abruptly as the path passes vertical. On a dense line chart, above and below can also leave a label between two lines, equally close to both (below, AAPL); only on with a halo is never ambiguous. So the default side is "on".

side as a candidate list

Because the chooser already takes candidates, side may be a list, tried in order, like QGIS's multi-select position flags:

A path that is a boundary

A region's boundary is a closed path with a known inside. On it, side is inset, outset or on, and at may name one of the mark's parts. Today's strings are exactly this on a rect: "outset-top" is Place.along({ at: "top", side: "outset" }). So the box vocabulary is not a separate geometry kind; it is along on a rect's boundary.

This pays off where a rect is not drawn as a box. In polar coordinates a rect's top part is the slice's outer arc, so a donut is labeled along its arcs with the same words. Today both .label("species") and position: "outset-top" on a donut put every label at one spot above the ring (#952): 

rect({ w: "count", fill: "species" }).label("species", {
  position: Place.along({ at: "top", side: "outset", orient: "curved" }),
})

A boundary with no named parts takes a fraction of its length or a starting direction, and the label slides along the outline until it is clear. Here each cluster's hull is labeled along its own outline, outside, then inside (where Sparrows is hidden because its dots fill the edge): 

polygon({ points: "ring", fill: "group", opacity: 0.18 }).label("group", {
  position: Place.along({ at: "top", side: "outset", orient: "curved" }),
})

Two vocabularies for "top"

The prototype first treated at: "top" as "the outline point farthest up the screen". That is wrong for a polar rect, whose top is its outer arc, not the top of the screen. The two meanings are different concepts, and both are needed:

Parts

belong to the mark · read by along

  • A rect declares top, right, bottom, left and its corners in its own frame, and the coordinate transform carries them.
  • A part is a stretch of the outline with a length, so a label that does not fit along it is hidden.
  • In polar coordinates, a rect's top is the outer arc.

Directions

belong to the screen · read by around

  • "The outline's extreme point toward the upper right" is a direction, with no length and no frame.
  • This is why around works on dots, polygons and hulls.
  • On a non-convex outline a direction can have several extreme runs (the C's right touches both arm tips); the rule takes the run nearest the middle of that side of the bounding box.

On a Cartesian rect the two agree, which is why today's strings never had to choose.

Rules the renders needed that the first draft did not state

  • orient: "curved" needs a true offset curve (the normal is averaged over a short stretch so an inset label does not fold at a sharp vertex) and a bend limit (a spot where the outline turns more than about 70° under the text is rejected), the same role the straightness check plays for "sloped".
  • A numeric at centers the label on that point (TikZ pos=0 also centers). at: "start" and at: "end" instead align the label's start or end with the path's end, so the label stays on the path.
  • With a list of sides, the chooser tries every side at one spot before sliding along the path, which keeps the label near at. The other order is decision 12.

06What the prototypes taught

One interior rule, not polylabel

Polylabel finds the point farthest from every edge, which is the center of the largest circle. Text is wide, so in C, U and L shapes it sends labels into the corner where two arms meet. Searching for the spot where the label's own box grows largest puts them in the middle of an arm, and it is the same rule d3-area-label uses for streamgraph bands. So interior() is one rule for bands and polygons.

Sloped inline labels need a smooth line

On raw monthly stock prices, the only stretches straight enough for a sloped label are the steep ones, and one label has nowhere to go. On smoothed data it works well. The member's docs should say so; Place.end() is the safer default for lines.

Along-line labels need a background

A halo works on charts; a small filled box reads better on diagram edges. This is a styling option of the label, decision 8.

Today's "center" can make a label vanish

When a shape's box center falls outside the shape (the C and the L), the label is colored for the inside (white) but drawn on the white background. This is a bug today, independent of this proposal.

Today's line and area labels read the box

.label() on a line or ribbon runs, but every label sits on its connector's bounding box, far from the line and overlapping. The "today" renders for lines and areas in section 03 show it.

07Approaches A, B, C

Three approaches differ in where the user writes a label. Two choices are shared by all three and are presented once, as separate axes: the Place strategy values (section 04) and the geometry queries (section 08).

A. .label() with a Place strategy

Recommended

The label stays a modifier on the mark (or operator) it describes. position takes a Place strategy, and an avoiding option names extra obstacles. 

// Point labels on a scatter
chart(countries)
  .flow(scatter({ x: "gdp", y: "lifeExpectancy" }))
  .mark(circle({ r: 3 }).label("name", { position: Place.around() }))

// End-of-line labels on a multi-series line chart
chart(stocks)
  .flow(group({ by: "symbol" }))
  .mark(line({ x: "date", y: "price", stroke: "symbol" }).label("symbol", { position: Place.end() }))

// Inline labels along the line
  .mark(line({ x: "date", y: "price", stroke: "symbol" })
    .label("symbol", { position: Place.along({ at: 0.6, orient: "sloped" }) }))

// Streamgraph band labels
chart(streams)
  .flow(spread({ by: "x", dir: "x" }), stack({ by: "series", dir: "y", alignment: "middle" }))
  .mark(blank({ h: "value" }))
  .layer(ribbon({ by: "series", fill: "series" }).label("series", { position: Place.interior() }))

// Labels that also stay off a trend line
  .mark(circle({ r: 3 }).label("name", { position: Place.around(), avoiding: selectAll("trend") }))
Desugars into

For each target t, .label(acc, { position: P, avoiding: O }) elaborates, as today, at t's parent into layer([ref(t), text(acc(t))]). What changes is who writes the text's position. A one-candidate strategy writes it with today's align and distribute constraints, so every existing position string means what it means now. A strategy with several candidates hands all labels from one .label() call to the chooser, which runs after the solve that places the targets and reads the targets, the labels placed so far and O as obstacles. The labels' boxes join the parent's box, as #707's box equation requires, and never touch a scale's domain.

Composes with

Operators: an operator .label() labels each group, as today. Coordinate transforms: a label is screen-space text (a label is not warped), so a path or region strategy must read the target's geometry after the coordinate transform; today that geometry only exists at lowering (open question 1). Animation: the label is attached to its target as today, so it tweens; a chooser that flips a label to another candidate between frames would jump, which is open question 3. Python: the same shape, with Place a family module like Curve.

Overlap

Defined as fusion into C, so the two cannot drift. B's anchors are the mechanism under its one-candidate strategies.

Trade-offs

Easy: the common case is one word on the mark you already wrote; defaults per geometry kind make .label("symbol") on a line do the right thing. Awkward: labeling marks of another chart, or a subset of a layer, still needs the hand-written tier. New terms: Place, avoiding (shared with #1152), and the member names.

B. Geometric anchors on refs, labels are plain constraints

No new labeling construct. Refs gain anchors computed from geometry, and a label is a text aligned to an anchor with the existing constraints. This is the TikZ and Bluefish model. 

layer([graph]).relate(({ edges }) =>
  edges.each((e) =>
    Constraint.align({ x: "middle", y: "middle", rotate: "tangent" },
      [e.at(Anchor.along(0.5)), text({ text: e.datum("weight") })])))

layer([lines]).relate(({ lines }) =>
  lines.each((l) =>
    Constraint.distribute({ dir: "x", spacing: 4 }, [l.at(Anchor.end()), text({ text: l.datum("symbol") })])))
Desugars into

Align and distribute, with anchors as new readable points on a ref.

Strength

Exact and general for diagrams; every anchor is reusable by arrows and connectors (#975 wants a ray-hit anchor for the same reason).

Weakness

No avoidance: choosing among spots is a search, and constraints are equations. It needs .each(), which is still open (#929). It is verbose for charts, where .label("symbol") is the whole intent.

Overlap

It is the mechanism under A's one-candidate strategies, so A can expose these anchors later without conflict.

C. A label tier

Runner-up

A label is its own relational construct in .layer() or .relate(), reading the previous tier's marks the way line and ribbon do. This is Vega's label transform on a text mark and Josh's labelLayout([ref(mark), text]). .label() becomes sugar for it, as .mark(line()) is sugar for .mark(blank()).layer(line()) (#748). 

chart(stocks)
  .flow(group({ by: "symbol" }))
  .mark(line({ x: "date", y: "price", stroke: "symbol" }))
  .layer(label("symbol", { position: Place.end() }))

// Label marks of another chart
chart(selectAll("hubs")).mark(label("name", { position: Place.around(), avoiding: selectAll("routes") }))
Desugars into

The same elaboration as A; A is defined as fusion into C.

Strength

The joint placement is visible: one tier owns a set of labels that avoid each other, and it can label marks from anywhere by name, which #803 asks for.

Weakness

A second spelling of the same idea, and its ink paints above its operands while every other relational mark paints below (#745's default), so it is the one relational construct that needs the opposite paint rule.

Overlap

Exact: A is defined as fusion into C, so the two cannot drift.

08Shared axis: geometry queries

Revised after review round 1 (section 05): one Outline query replaces the separate boundary and path queries.

The strategies need one query beyond enclosingCircle, added with its first consumer as shape-geometry.md decided. Open paths and region boundaries are one type, so they are one query: 

interface Outline {
  points: Point[];          // sampled, in screen space after the coordinate transform
  closed: boolean;          // a region's boundary (inside known by winding) or an open path
  parts?: { name: string; from: number; to: number }[]; // named arc-length ranges
}
interface HasOutline { outline?: (tolerance: number) => Outline[] }
  • closed decides the side vocabulary: inset/outset on a boundary, left/right on an open path.
  • parts are the mark's own named pieces, built in the mark's frame and carried through the coordinate transform: a rect names top, right, bottom, left and its four corners. In polar coordinates a rect's top part is a slice's outer arc. Shapes with no natural parts (circles, polygons, hulls) leave it empty.
  • A line, arrow or edge gives one open outline. An area or ribbon gives its closed band (read by interior) and its centerline as an open outline (read by along). This is #974's boundary with closed, parts and open paths added; enclose's private member reader becomes it (#1167).
  • It must be read after the coordinate transform, because labels are screen-space text. Today the transform runs only at lowering, so this query moves path transformation into layout for nodes whose outline is asked for (open question 1).

The chooser tests a label's box against obstacle geometry: discs for circles, segments for paths, outlines for regions, boxes for the rest, through a uniform grid like overlap's.

09Recommendation

Approach A, defined by rewrite into C, with B's anchors kept internal.

  • It desugars into the core. A one-candidate label is today's elaboration unchanged; a many-candidate label adds one search step of a kind the engine already has (overlap). The new surface is one strategy family and one option. (Principles: why keep the core small.)
  • One concept is one operator. The api-design page records that the earlier label design dropped a separate annotate() for options on label. Point, line and area labels are one concept to the user, and every precedent that unifies them (Vega, Mapbox, QGIS, Highcharts) does it with one construct and a geometry-driven strategy.
  • Meaning lives on the type. The default placement comes from the target's geometry kind, and a mismatch is a loud capability error, as api-design asks for data types.
  • A closed family plus a function hatch, like Curve, Overlap and Shape, spelled the same in JS and Python.
  • Overlaps are degenerate or exact. Today's strings are the one-candidate case. avoiding is #1152's option with the same value type. The chooser and Overlap.separate() share the obstacle reader and the grid, through #974.

Runner-up: C. If labeling marks from another chart, or a selected subset of a layer (label-syntax.md's last section, #803), turns out to be common, expose the label tier publicly. Nothing in A blocks that, since A is defined as fusion into it.

Out of scope here: leader lines and force-based repel (a later Place.repel() member that draws an arrow), labels outside a region with a connector (ggforce), and font size chosen to fit a region.

10Decisions for Josh

  1. Is the family named Place?

    As in Place.end(), or something else (Placement, Label)?

  2. Do today's position strings stay as shorthand for along on a rect's parts? revised in round 1

    "outset-top" = Place.along({ at: "top", side: "outset" }). I recommend they stay: a closed enum may be a string under the family rules, and they now have a definition.

  3. Is around the right name for the member that reads screen directions? revised in round 1

    Including the bar case Place.around({ candidates: ["outset-top", "inset-top"] }).

  4. Are the defaults by geometry kind OK?

    Dots → Place.around(), paths → Place.end(), regions → Place.interior(), boxes → "outset" as today. This changes scatter renders that use .label() today.

  5. How is a label with no free spot hidden?

    Silently, with a console note, or an error?

  6. Is avoiding shared with #1152, and do labels always avoid each other?

    avoiding is the same option name and value as #1152's (a list of refs or one selectAll), and labels from one .label() call always avoid each other and their own targets.

  7. Is the label tier (Approach C) public now?

    Or does it wait for a real example?

  8. How is a label's backdrop spelled?

    A halo (ggrepel bg.color, labellines outline_color) and a filled box (ggplot geom_label). Nesting suggests background: { fill, padding } and halo: { color, width } as label options.

  9. Does side take both frames? new in round 1

    above/below (screen) and left/right (direction of travel), plus on, and inset/outset on a boundary. above on a vertical stretch is no candidate, so the label falls to the next side in the list or is hidden. Default "on". OK?

  10. Keep parts and directions as two vocabularies? new in round 1

    at names the mark's own parts (a rect's top is a slice's outer arc in polar), while around uses screen directions. Keep the two vocabularies separate as proposed?

  11. Is orient spelled "horizontal" | "sloped" | "curved"? new in round 1

    It replaces the boolean sloped. Note it sits beside today's rotate (a fixed angle): does rotate stay as a fixed-angle override?

  12. With side as a list, which order does the chooser try? new in round 1

    Every side at one spot before sliding along the path (proposed), or slide along one side first?

  13. Do at: "start"/"end" align while a numeric at centers? new in round 1

    at: "start"/"end" align the label's start or end with the path's end, while numeric at centers it. OK, or one rule plus a separate align option?
