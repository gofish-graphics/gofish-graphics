GoFish API proposal

GoFish Annotations

Proposal. Approach C is not implemented; renders are of A and B, plus a prototype of parts of a mark. Syntax awaits sign-off on 18 decisions.
Round 2, 2026-11-01. Josh approved C overall. This round adds part / parts for selecting spans of a text without tokenizing it (example 5), and bands now use the existing x / x2 edges (example 2).
Rounds 3-4: how parts relates to partition, cut and anchors (#47).
Round 5: annotation styles table and key labels.
Summary

"Annotate" is not one primitive. Every annotation in the literature is a target plus some of three parts: a subject drawn on the target, a note, and a connector between them.

GoFish already has a construct for each part except the connector, so the proposal adds no annotate or callout operator.

It adds one label option, one data step, a way to select parts of a mark (spans of text, stretches of a line), one Shape member, and a few fixes, and it moves color emphasis into its own design.

Recommendation: Approach C

Write an annotation as a selection, a subject mark over it, and a .label() on that mark. The label is the note. A new leader option on .label() draws the connector. A new topK flow step selects extremes, and ref(x).part(sel) / .parts(sel) select parts of a mark. Color highlights are not annotations in this sense, because they restyle marks the annotation does not own. They stay a separate construct (#641). 

.layer(
  chart(selectAll("months"))
    .flow(topK(1, { by: "price" })) // selection
    .mark(
      enclose({ shape: Shape.oval(), padding: 6, fill: "none", stroke: RED }) // subject
        // note
        .label((d) => `Peak: $${project(d, "price")}`, {
          position: Place.around({ directions: ["nw"], offset: 40 }),
          leader: { stroke: RED }, // connector (new)
        })
    )
)

01Terms

Annotation
Ink added to a visualization to point out part of it, as opposed to the ink that encodes the data.
Target
What an annotation is about. It can be a set of marks (one point, a group, a series), a position in data space (y = 50, the summer of 2015), or another annotation.
Subject
Ink drawn on or around the target: a circle around a point, a box around a region, a blob around a group, a rule at a value. The word is d3-annotation's.
Note
The text of the annotation.
Connector
The line from the note to the subject or target.
Leader
A connector from a label to the thing it labels (also "leader line"). It is the cartography and drafting term. ggrepel calls it a segment, matplotlib calls it arrowprops.
Emphasis
Making some marks stand out by restyling them and the others (color, gray out, paint order). gghighlight and ChartMark treat it as a predicate that splits the marks into "selected" and "other".

03What the notes asked, and the answers

Question from the notes Answer
Is annotate a primitive? No. It is a set of constructs with one shared interface, like the graphical operators. The label design already rejected a separate annotate() (API Design, "One concept is one operator").
Are layouts, arrows and enclosures already expressible? Yes, all eight d3-annotation types render with today's primitives (see the grid). The cost is verbosity: a callout needs an outer layer, two Constraint.distribute calls and an arrow.
Do we need sugar like .label() and .emphasize()? Yes, but small: one leader option and one data step, sitting on existing constructs. No new top-level construct for callouts.
How do we balance brevity, readability and customization? Brevity comes from .label()'s automatic placement and avoidance. Customization comes from each part being an ordinary mark the user can swap. The data link holds because the target is a selection, not a pixel position. Practitioners asked for exactly this mix (Rahman et al., Designing Annotations, EuroVis 2026).
Where do color highlights fit? Outside this design, in #641. Emphasis restyles marks the annotation does not own and reshapes a shared color scale.

04Precedent

What matters for the design. The full survey with sources is research/prior-work.md.

  1. The same decomposition shows up everywhere. d3-annotation's named types are presets over subject, connector and note. AnnoGram has a target with optional text, enclosure, connector and indicator slots. matplotlib's annotate(text, xy, xytext, arrowprops) and Bluefish's Ref + Arrow + Align split it the same way.
  2. The type and the target are independent axes in every taxonomy. ChartAccent's target kinds (a data item by predicate, a coordinate, a chart element, another annotation) are reused by AnnoGram and ChartMark.
  3. Targets should be rules, not positions. ChartAccent participants liked targets that are "semantic based", that follow the data when it changes. Nine of ten practitioners in Designing Annotations finish their annotations in PowerPoint or Figma and lose the data link. They want automatic placement they can override without losing the binding.
  4. Emphasis is a different kind of thing. gghighlight, ChartMark ("opacity": {"selected": 1, "other": 0.5}) and Vega-Lite conditions all restyle the marks outside the target.
  5. The math side follows the same shape. Head et al. recommend keeping the augmentation apart from the formula. FFL is CSS-like: selector { color; label; label-marker: extent }. Delta (UIST 2026) keys labels by subexpression. TikZ uses pin for a note with a leader and fit for an enclosure.
  6. Nobody has tested authoring. AnnoGram's evaluation counts lines of code. ChartMark has no evaluation. So brevity is the only measured property, and it is a weak guide on its own.

Vega-Lite / Altair

Grammar. Syntax from memory

Decomposition: no annotation primitive. A rule or rect layer for reference lines and bands, a text layer for notes, no arrow mark. Highlight is a conditional encoding.

Bluefish

Pollock et al. UIST 2024

TikZ

LaTeX. From memory (standard)

1. Peak callout

GOOG monthly price

A circle around a line's maximum, a two-line note up and to the left, and a straight leader.

A · today39 lines · 315 tokens
  • The selection is honest: derive + maxBy over selectAll("months"), since there is no extremum selector (#796).
  • The note's text is computed outside the chart. A free note cannot read the selected row.
  • Two Constraint.distribute calls place the note. "Above" follows the axis direction.
  • The leader is an arrow, so it always has a head, and it ends on the bounding box (#975). 
layer([
  chart(goog, { schema: { date: Unit.time() }, w: 560, h: 300 })
    .flow(scatter({ by: "date", x: "date", y: "price" }))
    .mark(blank().name("months"))
    .layer(line({ stroke: "#467DA8", strokeWidth: 2 }))
    .layer(
      chart(selectAll("months"))
        .flow(derive((ms) => [maxBy(ms, (m) => project(m, "price"))]))
        .mark(
          enclose({
            shape: Shape.oval(),
            padding: 6,
            fill: "none",
            stroke: RED,
            strokeWidth: 1.5,
          }).name("peak")
        )
    ),
  spread({ dir: "y", spacing: 2, alignment: "start" }, [
    text({ text: "Peak", fontSize: 13, fontWeight: 700 }),
    text({ text: `$${peak.price} in ${monthYear(peak.date)}` }),
  ]).name("note"),
])
  .relate(({ peak, note }) => [
    Constraint.distribute({ dir: "x", spacing: 40 }, [note, peak]),
    Constraint.distribute({ dir: "y", spacing: 30 }, [peak, note]),
    arrow(
      {
        bow: 0,
        stretch: 0,
        strokeWidth: 1,
        padStart: 4,
        padEnd: 2,
        stroke: RED,
      },
      [note, peak]
    ),
  ])
  .render(container, { axes: true });

C · proposedtoday's spelling, two fixes, no new marks
Not implemented, not rendered

The expected picture is the A render (B is identical). C needs two fixes:

  • datum reads its value through the axis's column type, so an ISO date works on a time axis (today datum stores the raw value, so it needs epoch milliseconds).
  • A tier's fields stay out of the axis title, so the in-chart mean leaves the title as "temp".

A band is a rect with both edges given, x and x2, which rect already supports: the axis line is drawn as rect({ h: 1, x: datum(min), x2: datum(max) }), and x: "start", x2: "end" is tested on time columns. With no h it spans the plot.

Known limit: an align on x in the same layer drops a box placed by a data span (#1245). A rule or band name would save about one line per use, so the proposal does not add them.

C · proposedparts of a marknew in round 2

The formula is one text mark. A new ref method selects parts of it by substring, regex or character range, so the formula is never cut into tokens. The research note is research/span-selection.md.

  • ref(x).part(selector) gives one part and throws unless exactly one matches. ref(x).parts(selector) gives a list of refs. This is the ref / selectAll singular and plural pair. Each part's datum is { part, match, start, end }, so it flows as data like any selection.
  • It is not only for text. A part is a stretch of something the mark already has. For text that is its characters. For a path it is a stretch of its length (ref("route").part({ at: [0.2, 0.4] }), Place.along's words). For a line in data space it is a stretch of its data range (ref("price").part({ x: [datum(a), datum(b)] })). For a box it is a named outline edge (ref("bar").part("y-max"), the names from #1205).
  • Name. "part" follows CSS ::part and the outline parts from the label work. "span" is taken: it already means an extent in align({ x: "span" }).
  • Precedent. Systems either name parts when the text is written (CSS ::part, SVG tspan, \tikzmarknode, KaTeX \htmlId, Typst labels) or find them later by a rule (Typst show "E": ..., FFL selectors, DOM Ranges). The second kind keeps the formula whole, which is the point here. And the selection must return geometry (tikzmark, Typst pinit, Range.getClientRects()), not only a style hook as the CSS Highlight API does, because underlines and leaders need a shape to point at.
  • Not picked: named runs written into the text (Typst, tspan). That is still tokenizing by hand, and a line has no runs to name; it belongs with rich text (decision 7). A parts() flow step over selectAll is exactly derive(refs => refs.flatMap(r => r.parts(sel))), so it adds a name without adding power.
  • Subject. The bar under each term is Shape.bracket({ side }), a new Shape member. FFL calls it label-marker: extent, and TikZ draws it as a brace decoration.

How parts relates to partition, cut and anchors

new in rounds 3-4

Round 3 answers Josh's question about partition and cut. Round 4 compares parts with the anchors in the stacked-ribbons proposal (#47).

Parts, partition and cut

partition cut part / parts
input data rows by a key one drawn shape one drawn mark
space divided an axis (data space) the shape's extent along one direction the mark's own parameter: characters, arc length, data range, outline edges
coverage total, disjoint (cells) total, disjoint (a tiling) any subset, may overlap
returns groups, placed in their cells new ink (masked copies), placed by the parent refs: no ink, nothing moves

Discrete versus continuous does not separate them. Coverage does. It is the cell versus region refinement from #48: a cell is a region with the no-overlap and cover guarantee. partition and cut need cells, and parts needs only regions. The larger difference is the operand kind (#707). partition arranges fresh children, cut makes fresh ink, and parts returns refs. So they stay three operations. What they share is the selector.

  • parts also takes a cell system, as in ref("price").parts({ x: field("date").bin(Calendar.year) }). That is a cover of the line, one stretch per year.
  • cut(src, opts) is exactly ref(src).parts(cover) with each part made into mask(region, copy of src). That is what a slice is today. cut can be defined by that rewrite when #404's syntax is revisited. Its size weights then become one more cell system along a direction.
  • partition is unchanged. It divides an axis and places data.

Not prototyped. The cheap test is one line colored by yearly parts.

Parts and anchors

The stacked-ribbons proposal (#47, branch worktree-stacked-ribbons-proposal, not signed off) writes .anchor({ name, position: "x-max", slots: data(...).flow(stack(...)) }). That declares a named region on a boundary part and lays out slots along it. Ribbons attach by anchor name. Anchors and parts both name a region of a mark's own geometry, with the same part names. They differ in where the region comes from.

sketch
  • Built-in parts exist already: outline edges (x-max, r-min), a path's at range, and the label Place positions.
  • Declared parts are anchors. An anchor's position is a part selector. Its slots are a partition of that part into cells by a flow.
  • Found parts come from parts(selector): a substring, a regex, a data interval or a cell system.

So "a part of a mark" is one concept with three sources, and it should have one reference spelling. Today the anchors proposal writes a path step (nodes.out), and this proposal writes ref(x).part(sel). One option: .part(name) looks up built-in and declared parts by name, and patterns are explicit selectors (a regex, { text: "E" }, { x: [a, b] }). Then an anchor named "E" and the substring "E" cannot collide.

The anchors proposal's arrow rule ends at an anchor point and clips to the outline on the connection. That is also the rule for leader and the #975 fix, so the three should be built once. See decisions 13 and 14.

Under a coordinate transform it inherits .label()'s rules: Cartesian now, polar with #1201. Animation follows from labels being attached to their marks (#1206).
Easy
Callouts in about 12 lines. Notes read the selected rows, because a label reads its mark's data. Notes avoid each other and the data. Every part is swappable.
Awkward
A note with no subject needs something to hang the label on (decision 5). Notes with a bold title over a body need rich text in text (decision 7). Placement is directional (nw, 40 px) rather than an exact pixel offset (decision 3).
New terms
leader, topK, part / parts on refs, and Shape.bracket.
Cost to extend
A new subject is a new Shape member or any relational mark. A new connector route is a Curve member. A custom placement is a Place strategy (#1101).

09Overlap check for C

New piece Against Relation
leader arrow A small shared case. An arrow from a label to its target is a leader with a head. Both are built on one outline-clipped line (#975), so they cannot drift apart.
topK filter + derive An exact composition (sort by the key, take the first k). It is defined by that rewrite.
annotation subjects enclose Identical. The subject is an enclose.

10Recommendation: choose C

  • It desugars into the existing core. leader is a line in the label tier, and topK is sort and take. No new node kinds (Principles, "Why keep the core small").
  • One concept is one operator. The note stays .label(), so there is no second text placement path. The subject stays enclose, so there is no second shape list (API Design).
  • Few new terms, with precedent. "Leader" is the drafting and cartography word. topK is polars' top_k, which is the first precedent for data transforms in API Design. dplyr's slice_max is the alternative.
  • The data link holds. Targets are selections, which follow the data. This is the property ChartAccent's and Rahman's study participants asked for.
  • Customization keeps the existing families. Subjects are Shape members, leader routes are Curve members, and placements are Place members, each with #1101 as the escape hatch.
  • Same shape in JS and Python. leader is a dict like halo and background, and top_k is a flow step.

Runner-up: B as sugar over C

If real use shows that people write the same callout setup again and again, a callout preset can be added later as an exact rewrite into C: subject + label + leader. It should be built on .label(), not beside it as in the prototype.

What would change the pick: user tests where people cannot find "enclose + label + leader" and look for a word like "annotate" or "callout". A how-to page titled "Annotate a visualization" may cover that without a new name.

11Gaps found, independent of the approach

These hurt every approach, ranked by how much they hurt in the prototypes.

  1. #975: arrows end on the bounding box, not the outline. This broke example 4 and put elbow ends at centers.
  2. #521: there is no leader from a label to its target. That is what leader adds.
  3. A free note cannot read the selected row. A .label() on a selection tier already can (round 5 found this works), so C fixes this by making the note a label.
  4. #641: one emphasis is spelled three times (palette, zOrder, label test).
  5. #796: there is no extremum selector. That is what topK adds.
  6. mask reads its stencil's luminance, not its alpha, so a dark text stencil passes almost no color. .label() on a line drawn over a selection throws ("Place.end needs an open path").
  7. arrow cannot drop its head, and has no chart or bag form.
  8. Free notes do not avoid each other. C makes notes into labels, which do.
  9. datum("2015-06-01") on a time axis throws. It should read through the column type.
  10. A rule tier's field joins the axis title.
  11. #802 / #1203: operators and bare tiers cannot be named, which forces wrapper layers.

12Decisions for Josh

  1. Factoring.

    Annotation = selection + subject mark + .label(), with no annotate or callout name (C)? Or a bundled callout (B) now?

  2. leader spelling and default.

    leader: {} / leader: { stroke, curve, head }, off unless given? Or on automatically when a label lands more than some distance from its target, as ggrepel does?

  3. Far placement.

    Is Place.around({ directions, offset }) enough for callouts, or do callouts need an exact offset (Place.at({ dx, dy }), matplotlib's xytext in offset points)? "Up" must mean screen up, not the axis direction.

  4. Extremum step name.

    topK(k, { by }) and bottomK (polars), sliceMax (dplyr), or argmax?

  5. A note with no subject.

    Label the original mark with a predicate (#804's value-keyed record, .label({ AAPL: "..." })), or allow .label() on a bare selection tier with no drawn subject?

  6. Rules and bands.

    Keep them as rect + datum with x / x2 (no new marks), with the two fixes (datum reads ISO dates through the column type; tier fields stay out of the axis title)?

  7. Rich notes.

    A title line over a body line (d3-annotation's title + label). Is that a text feature (multi-line, spans) for a separate issue?

  8. Emphasis.

    Leave it to #641, with this survey's input that emphasis is a predicate that styles both the selected marks and the others?

  9. Brackets.

    Add Shape.bracket({ side }) for underbraces in math and diagrams?

  10. Parts of a mark.

    Is ref(x).part(sel) / .parts(sel) the right pair of names? Should parts take a record of named selectors, a list, or both?

  11. Part selectors.

    Text takes a substring, a regex or a [start, end] range. Should a line's part take a data interval, a length fraction, or both? Is a text part's shape its line box or its glyph ink?

  12. Coloring a part.

    mask (works today), a fill record on text, or emphasis (#641)?

  13. Shared selectors.

    Should parts accept cell systems (Bin, Calendar, weights), and should cut later be redefined as parts plus mask?

  14. Parts and anchors.

    One reference spelling for built-in, declared (anchor) and found parts: .part(name) for names with explicit pattern selectors, or the path step (nodes.out)? And design parts together with anchors (#47) rather than here?

  15. Key label name.

    key, footnote, or no new option and merge the notes into the legend?

  16. Marker style.

    Auto letters or numbers in reading order, a given marker (key: { marker: "A" }), or both? If auto, how do we pick letters or numbers?

  17. Where the key goes.

    Per label (key: { position }), or once per chart, like the legend?

  18. Badge shape.

    Let a label's background take a shape, background: { shape: Shape.oval() }, for the badge?
