Sums, products, and ribbons

A step back from spellings. What control-flow structure do parallel sets, sankeys and trees actually have, which parts of it GoFish already has, and which candidate constructs fill the gaps?

Companion to the stacked ribbons proposal. Precedent survey: proposals/stacked-ribbons/research/composition-precedent.md. Every picture is a real render from today's API unless marked otherwise; the spellings here are hypothetical.

What a good answer must do

  1. Compose without effort. Nesting one construct in another needs no glue.
  2. Fit known control flow. Each construct should be a familiar idea: sequencing, a loop, a tuple, a case split, recursion, a join.
  3. Fit the pipeline and direct style split. The flow is roughly a list monad; direct style is roughly tuple composition. A new construct should land on one side for a reason.
  4. Stay orthogonal to .map(). Host-language map stays the generic tool, and a new construct must not be map in disguise.

The structure underneath

The types from the pipeline-types essay say what the two styles are. A mark is Mark<T> = (d: T) => Node. A pipeline tier is spread(by) := mark => d => Spread(map(groupBy(d, by), mark)). A combinator in mark position is d => Spread([c1(d), c2(d), c3(d)]). So:

Pipeline tier = a sum

Its branches come from the data (groupBy), so the number of children is known only at run time. Each branch sees a part of the rows. In PL terms it is a monadic bind, or a case split over a data-dependent set of tags. Names are never needed, because each tier only rebinds "the current rows".

⇄

Direct-style combinator = a product

Its children are written in the spec, so the shape is static. Every child sees the same scope. In PL terms it is applicative fanout, Arrows' f &&& g &&& h. Children can differ from one another, which a sum's branches cannot.

The two connect by distributivity, rows × {class, sex, survived} ≅ rows + rows + rows. Fanning the rows out to three axis children (a product) and tagging each row once per axis, then splitting on the tag (a sum), describe the same picture. That is exactly how the two proposals relate. Proposal 2 keeps the fanout in the program. Proposal 1's unpivot moves it into the data as a tag column (axis), and spread({ by: "axis" }) is the case split on that tag.

This explains two earlier puzzles at once:

  • Why proposal 1 needed an id. Its unpivot copied rows. A fanout in the program shares them, so "same row, same ribbon" is free there.
  • Why proposal 1 broke parallel coordinates. Its value column lost what type it had. The honest type of a tagged view is a dependent pair, Σ f ∈ fields. T[f]: the type of the value depends on the tag. With the dependency kept, each axis has its own type, scale and title, and mm never meets g.

Control flow GoFish has, half has, and lacks

Control-flow idea Side GoFish construct Status Needed by
sequencing both .flow(a, b), nesting have everything
loop over data-derived groups sum by on any split have categories, nodes, links
tuple of different parts (fanout) product combinator children sharing the scope half two rows of nodes (school days, Beatles), FrankenSankey's parts
loop over a fixed set of fields product host .map (a Python comprehension) half parallel sets and coordinates, SPLOM
relation between two tables (node-link) both resolve + ribbon({ from, to, size }) allocating ends half sankeys, sankey tree, school days, Beatles, chord
projection into a sub-list, case split, recursion — chart(field("in")), match, a self-referring mark dropped no example left once sankeys and trees are node-link data
join branches by identity both ribbon/line over ends half every example

"Half": combinator children don't inherit the scope today (a one-line fix); sibling child charts share one scale; resolve exists but no ribbon allocates ends along an edge; ribbons join today only through an explicit selectAll + group tier, and run backwards when refs arrive out of order.

So no single side covers everything, and that's expected: lists and heterogeneous tuples are different data shapes. The one genuinely open row is the fixed family of fields, which sits on the distributivity line and could go either way. The candidates below are answers to that row. Where this points (revised). Criterion 4 means "don't build a second map", and literally using .map is fine. With that reading, A leads: it does well on all four criteria and adds no construct at all. A family of fields is a static product, and the host language already has the right tool for a static product generated from a list. C and D now overlap .map. B is the runner-up: the same picture from the sum side, worth having only as convenience for data that is already long, or for a spec that has to stay inside one flow. What A needs is the same plumbing B would need anyway: combinators passing their scope to chart() children, a scale per child that reads a different field, and the rejoin rule below. The sum/product reading still explains the split:

  • Sums live in the pipeline. Lists, and fixed families seen through a typed view, belong there.
  • Products live in direct style. Heterogeneous tuples belong there.
  • Distributivity is the bridge. It turns one into the other when a family's members are treated alike.

So the whole design reduces to the two styles GoFish already has, plus host .map. Lists go in the pipeline. Tuples, whether written out or generated with .map, go in direct style. Nothing new is needed for iteration; the new work is projection, per-child scales, and the rejoin rule.

The rejoin rule

One rule for every relational mark covers all the examples. A ribbon splits by keys that belong to the row, and treats keys that come from a view, plus the row itself, as its path.

  • Ribbon chart. lake and species are row keys. The path tier is lake, and the ribbon splits by species, which is today's #786 behavior unchanged.
  • Parallel sets. axis and category come from the view, so they form the path. The last stack has no by, so it splits per row: one ribbon per row, threaded across the axes. That's the case the fused form fails on today, and the rule fixes it from the view's typing rather than a heuristic.
  • Sankey. side and node come from the view over a link's source and target, so each link's two ends join.
  • Products (parallel sets and coordinates written with .map). Children share rows by reference, so ends from the same row join.
  • Node-link ribbons need no rejoin: each link row is one ribbon, and resolve has already named its two nodes.

In JS, identity is the object; on the wire, a row index is added when data enters chart(). That is what Vega-Lite users build by hand with window. ribbon({ by }) stays as the override for joining different rows, as in the chord's (i, j) with (j, i).

Node-link data: the ribbon allocates its ends

Revised after review. A sankey is a node-link diagram, which is the case resolve was built for. Nodes are placed by any chart. A links table's endpoint columns are resolved into refs to those nodes, and the ribbon takes from/to plus a size. At each node the ribbon ends stack along the facing edge, ordered by where the far node was placed. That drops the two things the earlier sankey spec needed and you rejected: field("in") in data position, and the spacing: 0 spread that faked a node out of two half-bars. Nodes are real marks again. It also solves the tree's open edge-slice problem, because a parent's edge is divided among its children by the same rule.

Real signature: resolve(cols, { from, key? }) replaces each listed column in place with the matching node ref. The default key is each node's innermost by field. All pictures below come from an emulation that rewrites the links into ribbon ends; in it, the far-end order is a proxy computed before layout (the far node's index), because today's API cannot read placed positions.

Energy sankey

layer([
  chart(nodes)
    .flow(spread({ by: "depth", dir: "x", spacing: 100 }),
          spread({ by: "name", dir: "y", spacing: 10 }))
    .mark(rect({ w: 12, h: "value" }).name("nodes")),
  chart(links)
    .flow(resolve(["source", "target"], { from: selectAll("nodes") }))
    .mark(ribbon({ from: "source", to: "target", size: "value", opacity: 0.5 })),
])

The d3-sankey inputs, used as they are: no nest join, no ends table.

Sankey tree

layer([
  chart(treeNodes)   // { key, depth, class, sub, leaf, count }
    .flow(spread({ by: "class", dir: "y", spacing: 8 }),
          spread({ by: "depth", dir: "x", spacing: 64, alignment: "middle" }),
          spread({ by: "sub", dir: "y", spacing: 4 }),
          spread({ by: "leaf", dir: "y", spacing: 2 }))
    .mark(rect({ w: 40, h: "count", fill: "class" }).name("nodes")),
  chart(treeLinks)   // { source: parent key, target: child key, value }
    .flow(resolve(["source", "target"], { from: selectAll("nodes"), key: "key" }))
    .mark(ribbon({ from: "source", to: "target", size: "value", fill: "color", opacity: 0.6 })),
])

Each parent's right edge is divided among its children's ribbons automatically. class is nested outside depth: the other way round, the gaps add up differently in each column and the ribbons bend. key: "key" is needed because the innermost tier (leaf) is blank for most nodes.

Beatles: equal-size ends on a line

layer([
  spread({ dir: "y", spacing: 260 }, [
    chart(credits).flow(spread({ by: "song", dir: "x", spacing: 18 }))

    chart(credits).flow(spread({ by: field("writer").sort(WRITERS), dir: "x", spacing: 90 }))

ends: spread() gives equal slots along the head's edge; ends: stack() (the default when there is a size) gives value-sized, touching ends. The choice reuses the existing stack/spread distinction instead of a flag.

FrankenSankey: an end-order override

layer([
  spread({ dir: "x", spacing: 150, alignment: "end" }, [
    spread({ dir: "x", spacing: 0, alignment: "end" }, [
      chart(years).flow(spread({ by: "year", dir: "x", spacing: 22 }), stack({ by: "decision", dir: "y" }))
        .mark(rect({ w: 0, h: "value", fill: "decision" }).name("area")),
      chart([{ name: "2017", total: total2017 }]).mark(rect({ w: 14, h: "total" }).name("nodes")),
    ]),
    chart(countries).flow(spread({ by: "name", dir: "y", spacing: 6 }))
      .mark(rect({ w: 14, h: "total" }).name("nodes")),
  ]),
  chart(selectAll("area")).flow(group({ by: "decision" })).mark(ribbon({ fill: "decision" })),
  chart(links)   // { source: "2017", target: country, decision, value }
    .flow(resolve(["source", "target"], { from: selectAll("nodes"), key: "name" }))
    .mark(ribbon({ from: "source", to: "target", size: "value", fill: "decision", opacity: 0.55,
      ends: { from: stack({ by: field("decision").sort(DECISIONS) }),
              to: stack({ by: field("decision").sort(DECISIONS) }) } })),
])

At the 2017 bar the ends go decision first; at each country they go by decision too. ends: stack({ by }) groups the ends in its sort order, and the far node's position orders them within each group. d3's linkSort is one comparator for every node and both sides, so it can't say this; ggalluvial's geom_flow (each node orders its own ends) is the precedent. One alternative removes the override entirely: if the bar is two nodes (the area's two 2017 cells), the default order is already right, and the bar is two-colored as in the FT original.

Chord: asymmetric ends on one part

layer({ coord: Coord.clock() }, [
  chart(groups)
    .flow(spread({ by: field("name").sort(NAMES), dir: "x", spacing: 0.04, y: 160, h: 16 }))
    .mark(rect({ w: "total", fill: "name" }).name("nodes")),
  chart(pairs)   // { a, b, ab, ba, lead }, with a <= b
    .flow(resolve(["a", "b"], { from: selectAll("nodes") }))
    .mark(ribbon({ from: "a", to: "b", size: { from: "ab", to: "ba" },
                   at: "bottom", curve: Curve.chord(), fill: "lead", opacity: 0.67 })),
])

A chord's two ends have different widths, so size takes one per end. Both ends sit on the inner arc (at: "bottom"; the spelling for choosing a part is still open), and ends on the same part are ranked together. On a cycle, far position is measured around the circle, (i − j) mod N, which crosses less than d3's order. A self chord gets one end. Curve.chord() is a placeholder name for the throwaway curve.

The case split goes away. The FrankenSankey no longer needs a sum with different branches, so match has no motivating example left. The two shapes that remain are node-link data (this section) and rows across a fixed family of fields, the candidates above.

Open questions

  1. Does the sum/product reading match your intuition for the pipeline vs direct-style split: data-dependent branches in the pipeline, static tuples in direct style?
  2. Candidate A: are products generated with host .map (a Python comprehension) the answer for fixed families of fields, with a typed unpivot view (B) kept only as optional convenience, or dropped?
  3. Per-child scales: should a direct-style child chart that reads a different field get its own scale and axis title by default, with a way to ask for a shared one? (Under B this would instead be dependent typing of value.)
  4. Rejoin: one rule for relational marks, splitting by row-level keys while view-level keys and row identity form the path, with ribbon({ by }) as the override?
  5. Node-link ribbons: ribbon({ from, to, size }) after resolve, with ends stacked along the facing edge by the far node's placed position, as the spelling for sankeys, sankey trees and chords?
  6. End layout and order: ends: stack() / ends: spread() (reusing the operators, per side as { from, to }), with stack({ by }) as the order override? Or a separate order option?
  7. Choosing a part (the chord's inner arc): a part name per side on the ribbon, or something else, given that .at didn't land?
  8. Node versus ends: a node smaller than its ends is a loud error, and a larger one leaves slack at the part's start. Is that the rule, and should the slack anchor be configurable?
