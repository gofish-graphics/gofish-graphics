Anchors

Your idea, worked through with you in review. A mark gets named anchors, which are intervals or points laid out along one part of its boundary. Ribbons, lines and labels attach to them. Stacking is real again, and it lives on the node's edge, where you would point to it. The ribbon goes back to a one-to-one band between two anchors, and its width is their size. 

rect({ w: 12, h: "value" }).anchor({
  name: "out", // first, so a search finds it
  position: "x-max", // where: as in .label(text, { position })
  slots: data(links, { on: "source" }).flow(stack({ size: "value" })), // what and how: rows, then a flow
});
Field Meaning Where it comes from
name What ribbons, lines and labels refer to. Written first by convention.
position A part name: the side of the mark whose 1D space the slots are laid out in: x-min, x-max, y-min, y-max, or the coordinate's own dimension names (r-min is a polar rect's inner arc). The position key of .label(); the label proposal's Place.along; GoFish's min/max box anchors; dimension names from #838.
slots The rows, then how they are arranged. data() is the mark's own rows. data(table, { on }) is the rows of another table whose on column refers to this mark. .flow(...) is ordinary operators with their ordinary size, spacing and by; dir comes from the part. Without slots, there's one anchor covering the whole side. data pairs with datum (rows and one value); on as in polars and SQL joins; the operators from the mosaic.

Four rules:

  • Sizes come from the operators. A slot's size is stack({ size }) or spread({ size }), measured on the host mark's own scale along that side, because it's the same measure. A node bigger than its slots leaves slack; slots longer than the node are a loud error.
  • Without a size, slots are points. spread({ spacing }) sets their pitch.
  • Ribbons and lines refer to anchors by mark name, then anchor name: ribbon({ from: "nodes.out", to: "nodes.in" }). The ribbon for a row runs from the slot holding that row in a nodes.out anchor to the slot holding it in a nodes.in anchor (how this resolves).
  • A row in several anchors of the same names is threaded in layout order. This is the parallel-sets case.

Referring to anchors: <markName>.<anchorName>

A ribbon or line names an anchor by the mark's name, then the anchor's name: ribbon({ from: "nodes.out", to: "nodes.in" }). This is GoFish's existing reference path API, which already walks into a mark's scope by tag: ref(token).tag1[i].tag2, or the array form ref([token, "tag1", i, "tag2"]). An anchor is a tag in its mark's scope, so "nodes.out" is a path with two steps.

It resolves in three steps:

  1. The mark: every mark named nodes. The name is plural, as in selectAll("nodes").
  2. The anchor: the out anchor inside each of them, which gives a selection of anchors.
  3. The slot: for the ribbon drawn from a given link row, the one slot that holds that row. There is exactly one, because data(links, { on: "source" }) put each link into its source node's out anchor. A row in two such slots, or in none, is a loud error.

So the join is declared once, on the anchor, and the ribbon needs no resolve. The precise form of the shorthand is a path on a selection, from: selectAll("nodes").out, the same proxy style as ref(token).tag. It would need selectAll to be usable outside chart data, which today it isn't.

The alternative is to resolve the mark, then the anchor. The links are resolved to nodes first, and the path starts from the row's column: 

chart(links)
  .flow(resolve(["source", "target"], { from: selectAll("nodes") }))
  .mark(ribbon({ from: ["source", "out"], to: ["target", "in"] })); // the array path form

This says the same join in a second place. The ribbon's resolve would make each anchor's data(links, { on }) redundant, so one of the two has to go. I'd keep the join on the anchor and the qualified name on the ribbon. That keeps the anchor's data flow visible where its stacking happens, which you asked for, and the ribbon reads like the picture. One loose end: a dot in a name position is a scope step ("nodes.out"), while a dot after datum in by is a field path ("datum.lake"). Both mean "walk into", but the overlap needs a stated rule.

Energy sankey: rows from the links table

GoFish (anchors)
layer([
  chart(nodes)
    .flow(
      spread({ by: "depth", dir: "x", spacing: 100 }),
      spread({ by: "name", dir: "y", spacing: 10 })
    )
    .mark(
      rect({ w: 12, h: "value" })
        .anchor({
          name: "in",
          position: "x-min",
          slots: data(links, { on: "target" }).flow(stack({ size: "value" })),
        })
        .anchor({
          name: "out",
          position: "x-max",
          slots: data(links, { on: "source" }).flow(stack({ size: "value" })),
        })
        .name("nodes")
    ),
  chart(links).mark(
    ribbon({ from: "nodes.out", to: "nodes.in", opacity: 0.5 })
  ),
]);

data(links, { on: "source" }) is the reverse of resolve: resolve gives a link its node, and on gives a node its links. Both match on the node's key. Slot order defaults to where the far node was placed. Open: the node's value (the larger of its two sides) still comes from data, because reading it from the anchors is a cycle.

There is no separate bar. The stacked area's 2017 column already holds one cell per decision, and those cells carry the out anchor, so the sankey leaves the area's last slice directly. Every area cell has the anchor, but only the 2017 cells get rows.

What still needs deciding

  • Slack placement. Where a block of slots sits on a side longer than it: the part's start by default (d3's rule). The word for overriding it is open, since alignment means the cross axis in spread.
  • Node value. A sankey node is as tall as its larger side, which has to come from data (a column or a data helper).
  • Part names. Labels still use top/right. Using axis-relative names for both is one decision across the two proposals, together with Place.along's at.
  • Name scope. Anchor names need a scoping rule next to .name(). On the wire, the join and the row lookup need the system's row index.
  • The chord. Whether gaps grow the group or shrink the slots, and the unit of a spacing inside a polar side.

How the spelling got here: chart().flow().mark(blank()) inside the modifier (it reused words that mean drawing); cut-style options (the stacking was invisible); a chained .along().flow() (the name came last and the chain didn't nest when formatted); size on the context (it didn't match how size works elsewhere); along(part) in position with the rows and flow in slots; and finally the along wrapper dropped, so position is just the part name (this version).

Reading. Proposal 5 is the only one with no workarounds across the suite, and the only one that serves labels with the same mechanism. Its stacking is a real operator in a real flow, and its words all come from elsewhere in GoFish: position from labels, size, spacing and by from the operators, on from joins, and data alongside datum. The sankey also needs no resolve. Its costs: two new names (.anchor and data); a shared decision with the label proposal about part names and about sharing them with Place.along's at; a word for where slots sit when a node has slack; and a node value that still comes from data. Node-link allocation (3) is the runner-up: it is as clean on the examples, but hides the stack inside the ribbon. Proposal 5 is proposal 3 with the allocation moved onto the node and written as a flow.

Three things can then be defined by rewrite instead of by special code. The principles essay says axes and labels "desugar in spirit more than in implementation", and that "the aspiration is to fold both into the same scheme". Anchors could be that scheme.

1. chart() is a data flow in a 2D space

How we got here

The exploration that led to anchors: the criteria, the sum/product reading, the candidates for repeating over fields, the rejoin rule, and node-link ribbons. Kept for the reasoning; the current design is above.

What a good answer must do

  1. Compose without effort. Nesting one construct in another needs no glue.
  2. Fit known control flow. Each construct should be a familiar idea: sequencing, a loop, a tuple, a case split, recursion, a join.
  3. Fit the pipeline and direct style split. The flow is roughly a list monad; direct style is roughly tuple composition. A new construct should land on one side for a reason.
  4. Stay orthogonal to .map(). Host-language map stays the generic tool, and a new construct must not be map in disguise.

The structure underneath

The types from the pipeline-types essay say what the two styles are. A mark is Mark<T> = (d: T) => Node. A pipeline tier is spread(by) := mark => d => Spread(map(groupBy(d, by), mark)). A combinator in mark position is d => Spread([c1(d), c2(d), c3(d)]). So:

Pipeline tier = a sum

Its branches come from the data (groupBy), so the number of children is known only at run time. Each branch sees a part of the rows. In PL terms it is a monadic bind, or a case split over a data-dependent set of tags. Names are never needed, because each tier only rebinds "the current rows".

⇄

Direct-style combinator = a product

Its children are written in the spec, so the shape is static. Every child sees the same scope. In PL terms it is applicative fanout, Arrows' f &&& g &&& h. Children can differ from one another, which a sum's branches cannot.

The two connect by distributivity, rows × {class, sex, survived} ≅ rows + rows + rows. Fanning the rows out to three axis children (a product) and tagging each row once per axis, then splitting on the tag (a sum), describe the same picture. That is exactly how the two proposals relate. Proposal 2 keeps the fanout in the program. Proposal 1's unpivot moves it into the data as a tag column (axis), and spread({ by: "axis" }) is the case split on that tag.

This explains two earlier puzzles at once:

  • Why proposal 1 needed an id. Its unpivot copied rows. A fanout in the program shares them, so "same row, same ribbon" is free there.
  • Why proposal 1 broke parallel coordinates. Its value column lost what type it had. The honest type of a tagged view is a dependent pair, Σ f ∈ fields. T[f]: the type of the value depends on the tag. With the dependency kept, each axis has its own type, scale and title, and mm never meets g.

Where this points (revised). Criterion 4 means "don't build a second map", and literally using .map is fine. With that reading, A leads: it does well on all four criteria and adds no construct at all. A family of fields is a static product, and the host language already has the right tool for a static product generated from a list. C and D now overlap .map. B is the runner-up: the same picture from the sum side, worth having only as convenience for data that is already long, or for a spec that has to stay inside one flow. What A needs is the same plumbing B would need anyway: combinators passing their scope to chart() children, a scale per child that reads a different field, and the rejoin rule below. The sum/product reading still explains the split:

  • Sums live in the pipeline. Lists, and fixed families seen through a typed view, belong there.
  • Products live in direct style. Heterogeneous tuples belong there.
  • Distributivity is the bridge. It turns one into the other when a family's members are treated alike.

So the whole design reduces to the two styles GoFish already has, plus host .map. Lists go in the pipeline. Tuples, whether written out or generated with .map, go in direct style. Nothing new is needed for iteration; the new work is projection, per-child scales, and the rejoin rule.

The rejoin rule

One rule for every relational mark covers all the examples. A ribbon splits by keys that belong to the row, and treats keys that come from a view, plus the row itself, as its path.

  • Ribbon chart. lake and species are row keys. The path tier is lake, and the ribbon splits by species, which is today's #786 behavior unchanged.
  • Parallel sets. axis and category come from the view, so they form the path. The last stack has no by, so it splits per row: one ribbon per row, threaded across the axes. That's the case the fused form fails on today, and the rule fixes it from the view's typing rather than a heuristic.
  • Sankey. side and node come from the view over a link's source and target, so each link's two ends join.
  • Products (parallel sets and coordinates written with .map). Children share rows by reference, so ends from the same row join.
  • Node-link ribbons need no rejoin: each link row is one ribbon, and resolve has already named its two nodes.

In JS, identity is the object; on the wire, a row index is added when data enters chart(). That is what Vega-Lite users build by hand with window. ribbon({ by }) stays as the override for joining different rows, as in the chord's (i, j) with (j, i).

Node-link data: the ribbon allocates its ends

Revised after review. A sankey is a node-link diagram, which is the case resolve was built for. Nodes are placed by any chart. A links table's endpoint columns are resolved into refs to those nodes, and the ribbon takes from/to plus a size. At each node the ribbon ends stack along the facing edge, ordered by where the far node was placed. That drops the two things the earlier sankey spec needed and you rejected: field("in") in data position, and the spacing: 0 spread that faked a node out of two half-bars. Nodes are real marks again. It also solves the tree's open edge-slice problem, because a parent's edge is divided among its children by the same rule.

Real signature: resolve(cols, { from, key? }) replaces each listed column in place with the matching node ref. The default key is each node's innermost by field. All pictures below come from an emulation that rewrites the links into ribbon ends; in it, the far-end order is a proxy computed before layout (the far node's index), because today's API cannot read placed positions.

A chord's two ends have different widths, so size takes one per end. Both ends sit on the inner arc (at: "bottom"; the spelling for choosing a part is still open), and ends on the same part are ranked together. On a cycle, far position is measured around the circle, (i − j) mod N, which crosses less than d3's order. A self chord gets one end. Curve.chord() is a placeholder name for the throwaway curve.

Open questions

  1. Does the sum/product reading match your intuition for the pipeline vs direct-style split: data-dependent branches in the pipeline, static tuples in direct style?
  2. Candidate A: are products generated with host .map (a Python comprehension) the answer for fixed families of fields, with a typed unpivot view (B) kept only as optional convenience, or dropped?
  3. Per-child scales: should a direct-style child chart that reads a different field get its own scale and axis title by default, with a way to ask for a shared one? (Under B this would instead be dependent typing of value.)
  4. Rejoin: one rule for relational marks, splitting by row-level keys while view-level keys and row identity form the path, with ribbon({ by }) as the override?
  5. Node-link ribbons: ribbon({ from, to, size }) after resolve, with ends stacked along the facing edge by the far node's placed position, as the spelling for sankeys, sankey trees and chords?
  6. End layout and order: ends: stack() / ends: spread() (reusing the operators, per side as { from, to }), with stack({ by }) as the order override? Or a separate order option?
  7. Choosing a part (the chord's inner arc): a part name per side on the ribbon, or something else, given that .at didn't land?
  8. Node versus ends: a node smaller than its ends is a loud error, and a larger one leaves slack at the part's start. Is that the rule, and should the slack anchor be configurable?
