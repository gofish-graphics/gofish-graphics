Stacked and divided ribbons

A sankey is a stacked area chart whose stacks are nodes. Each ribbon end is a data row, the ends stack inside their node with the ordinary stack operator, and the ribbon stays one-to-one.

  1. Prototypes drew parallel sets, a sankey tree, and the full 48-node energy sankey with no core change, using today's stack, spread and ribbon.
  2. What is missing is small: a unpivot data helper, ribbon({ by }) to name which rows form one ribbon, and, for chord diagrams, ribbon({ at }) to say which part of a node each end attaches to.
  3. The runner-up has the ribbon allocate its own ends on nodes placed by anything: ribbon({ from, to, size }). It wins if ribbons over independently placed nodes become a priority.
Recommendation: Approach B, ends are rows. Span allocation is the flow's stack, so it desugars into the existing core, keeps one stacking mechanism, and realizes the direction recorded in #745: ribbons one-to-one per row, plus per-edge span allocation.

Update after review: Round 2 explores syntax that follows the data's shape (a record becomes direct-style children, a list becomes a flow), with rendered prototypes and four new decisions (9 to 12). Side-by-side specs. Back to the drawing board: Sums, products, and ribbons reframes both proposals as two sides of one structure.

Proposal 2 is round 2, "syntax follows the data": a list becomes a flow and a record becomes direct-style children. Both are written in their target spellings. What the harder references say

  • Two different rows favor proposal 2 (three of four). When the two sides of a gap differ in spacing, size, order or labels, proposal 1's single node tier forces them to share. Proposal 2 gives each side its own flow, and each side's end order falls out of that flow with no rank key.
  • A matrix favors proposal 1. When the data's rows already are the ends, as in a chord, the flat flow is the natural spelling.
  • They are not exclusive. Proposal 2 still needs proposal 1's explicit ribbon({ by }) for pairings that object identity cannot express.
  • New cross-cutting requirements:
    • a shared-or-independent value scale per child chart (proposal 2 relies on sibling charts sharing one, which the docs say they should not);
    • a ribbon that uses facing edges whatever order its refs come in;
    • end order that differs per side of a gap;
    • equal-size ends as an option next to value-sized ends;
    • image nodes.
  • A new bug: an accessor size is put through the scale. w: 14 draws 14 px, but w: (d) => 14 draws 36 px. So a table with several kinds of rows cannot give each kind a fixed pixel size.

Terms

Node
A bar or arc whose length shows a total: a sankey node, a parallel-sets category, a chord group.
Link
One flow between two nodes, with a value.
End
The interval where one link meets one node. ggalluvial calls it a lode, d3-chord a subgroup, ELK and Graphviz a port.
Path
The chain of ends one ribbon threads: two for a sankey link, one per axis for a parallel-sets cohort.
Part
A named piece of a mark's outline that the mark declares: a rect's top, right, bottom, left. The coordinate transform carries parts along, so a polar rect's bottom is its inner arc. Same word as in the label proposal.
Unpivot
Turn columns into rows: a row with source and target becomes two rows with a side column. The polars name; dplyr says pivot_longer. Worked example below.

What unpivot does

unpivot takes some columns of a table and turns them into rows. For each input row, and for each column named in on, it writes one output row. That output row gets:

  • a column named by variable, holding the name of the column it came from;
  • a column named by value, holding that column's value in the input row;
  • a column named by id, holding the input row's position, so every output row remembers which input row it came from;
  • a copy of every column that is not in on.

The columns in on themselves are dropped. So a table of n rows unpivoted on k columns becomes n × k rows. Nothing is added up or lost: it is the same data, reshaped from wide to long.

Here it does one job: it turns "one row per link" into "one row per end". The id column is what lets the ribbon find the ends that belong together later, through ribbon({ by: id }).

Example 1: a sankey link has two ends

Three real links from the energy data, all touching the node Coal:

Input: one row per link
source target value
Coal imports Coal 11.606
Coal reserves Coal 63.965
Coal Solid 75.571 
unpivot({
  on: ["source", "target"],
  variable: "side",
  value: "node",
  id: "link",
});
Output: one row per end
link side node value
0 source Coal imports 11.606
0 target Coal 11.606
1 source Coal reserves 63.965
1 target Coal 63.965
2 source Coal 75.571
2 target Solid 75.571

Read the output column by column. side holds the old column names, node holds the old values, and link numbers the input rows. value was not in on, so it is copied onto both ends of its link.

Now Coal has three rows of its own. The flow groups rows by node, splits each node by side, and stacks the rows on each side. Coal's two incoming ends stack on its left (11.606 + 63.965 = 75.571), and its one outgoing end fills its right. Then ribbon({ by: "link" }) joins the two rows that share a link number. For link 1, that is the Coal reserves row and the lower-left end of Coal.

Example 2: a parallel-sets cohort has one end per axis

Two real rows of the titanic table. Each row is a cohort of passengers, and each of its three category columns becomes one end:

class sex survived count
First Female Yes 141
First Male Yes 62 
unpivot({

path axis category count

spread({ by: "axis" }) makes the three columns of the picture, and spread({ by: "category" }) makes the boxes inside each column. Both cohorts land in the same First box (141 + 62 stacked) and the same Yes box. They split apart only on the sex axis. One ribbon per path threads that cohort's three rows from left to right. This is ggalluvial's "lodes form", and ggforce's gather_set_data and ggsankey's make_long do the same reshape.

Two notes on the spelling, both part of decision 3. Polars has no id option: there you would add the row number first with with_row_index. And value: "node" names the new column, which is easy to confuse with a data column that is itself called value, as in the energy links. dplyr's names_to / values_to spelling avoids that confusion, at the cost of leaving the polars names.

Your questions, answered

From the notes Answer
Extend the existing ribbon API? Yes, by two options: by (which rows form one ribbon) and at (which part each end attaches to). The span allocation itself does not live on the ribbon.
The stack operator, or a method like ribbon().stack()? The stack operator, applied to the ends inside each node. ribbon().stack() is Approach C below: it would be a second route to stacking next to the flow's stack, which matches the #290 note that a mark-side stack on a connector can only respell a row stack.
What do enclose, line, cut and labels contribute? line: the same ends give parallel coordinates and stringlines. enclose: draws a node box when in-sum and out-sum differ (Shape.box(), padding 0). cut: another way to make ends when the node is one drawn shape such as an image; for a rect it equals stacking the ends. labels: node labels are .label() on the node tier, ribbon labels are Place.along, and at reuses the label proposal's part names.
One-to-many, many-to-many? Ribbons stay one-to-one per link. Splits and merges come from several ends stacking in one node. The energy sankey (69 links, splits and merges) renders this way.

Today

A ribbon spans the full facing edge of each operand's box. No option attaches it to part of an edge, so every divided-end example builds one node per end and lists ribbons by name. The gallery Sankey Tree is about 137 lines for this reason.

Prior work

Every system that draws sankeys correctly stacks link values inside each node and then joins two intervals. The one general grammar without ends, Mascot, attaches every link at its node's middle and gets a thick-edged node-link diagram instead.

ggforce

gather_set_data makes long data. One gap, one curvature.

ggsankey

make_long gives one row per edge. Sankey and alluvial differ only by gap and baseline.

geom_sankey(flow.alpha = .6, space = 10)

circlize / d3-chord

Sectors sized by total; links stacked in sectors. d3's ribbon() joins two angle intervals through the center.

Mascot (foil)

No end concept: every link leaves its node's middle, so widths pile up instead of tiling the edge. 

sourceAnchor: ["right", "middle"];
encode(link, "strokeWidth", "value");

Also surveyed: TikZ sankey (\sankeyfork{a}{25/b,10/c} divides a cross-section into sub-intervals that must sum to the parent, the closest model to this proposal), the Kibana Vega sankey (stack + lookup + linkpath, with node and slot stacks kept in sync only by a shared sort key), ELK port constraints (a ladder of who owns end order), Plotly, Highcharts, ECharts, networkD3, RAWGraphs, Kosara's Parallel Sets. Fixed chart types such as geom_sankey and go.Sankey are foils: they list arrangements instead of composing them.

How B composes

Desugars into

  • unpivot is a derive data helper.
  • by, at are ribbon options.
  • Span allocation is stack. Node and ribbon share one scale by construction, since the ends are the node.
  • Polar works once at exists.
  • line({ by }) over the same ends gives parallel coordinates.

Overlap check

  • stack: exact composition; the end stack is a stack.
  • cut: degenerate; for a rect node, cutting by link values equals stacking ends. Cut stays the tool for an image node.
  • enclose: none; it draws node boxes.
  • #786 default split: by overrides it only when named.

Trade-offs

  • Easy: no new layout; cohort identity across axes is free; chords and sankeys share one spec shape.
  • Awkward: users think of ends as rows; end order needs a sort key that agrees with the far node; ribbons cannot attach to nodes the flow did not lay out.
  • New terms: unpivot, by, at, all existing words.

Round 2: syntax that follows the data

ExploringFrom the review discussion. Rendered with today's API; callback-free spellings are emulated with story-local helpers and marked so.

The shape of the data picks the syntax. spread already has both forms, so nothing new is needed for the rule itself:

Data shape Syntax Example
a list (rows, groups) a flow tier with by: the operator iterates the categories on one axis; the links at one node
a record (a fixed set of fields) the direct-style combinator, one child per field the axes of parallel sets (a record of columns); a node's (in, out) pair

Parallel sets is a record of axes, each a list of categories, each a list of rows. A sankey is a list of nodes, each a pair (in-links, out-links), each a list of links: d3-sankey's node.targetLinks and node.sourceLinks. A sankey tree is the same thing recursively. Rows are never copied, so every end of one row is the same datum, and "same datum, same ribbon" pairs them with no unpivot and no id. The PL precedent is "the template follows the data definition" from How to Design Programs.

Removing the callback: the equivalent of group({ by })

The .map(callback) hides two different iterations. Each has a callback-free precedent, and both render pixel-identical to the versions above (emulated with story-local helpers).

1. Over columns: expression expansion
const axes = cols(["class", "sex", "survived"]);
chart(titanic)
  .mark(
    spread({ dir: "x", spacing: 120 }, [
      chart()
        .flow(spread({ by: axes, dir: "y", spacing: 12 }), stack({ dir: "y" }))
        .mark(rect({ w: 12, h: "count", fill: "class" })),
    ])
  )
  .layer(ribbon({ opacity: 0.6 }));

A child that mentions a multi-column value stands for one child per column, the way polars expands pl.col(["a", "b"]).sum() into one expression per column (dplyr: across). The expansion happens only in a combinator's child list, so a tuple of columns becomes a tuple of children. Two multi-column values in one child must have the same length and zip.

2. Over a parent's sub-list: nested data
chart(nodes) // { name, depth, in: [links], out: [links] }
  .flow(
    spread({ by: "depth", dir: "x", spacing: 100 }),
    spread({ by: "name", dir: "y", spacing: 10 })
  )
  .mark(
    spread({ dir: "x", spacing: 0 }, [
      chart(field("in"))
        .flow(stack({ dir: "y" }))
        .mark(rect({ w: 6, h: "value" })),
      chart(field("out"))
        .flow(stack({ dir: "y" }))
        .mark(rect({ w: 6, h: "value" })),
    ])
  )
  .layer(ribbon({ opacity: 0.4 }));

A child's data is a list field of the parent row, as in d3's nested selections (selection.data(d => d.children)). The emulation spells it chart().flow(unnest("in"), ...). A sankey tree is this rule applied recursively to a children field.

What round 2 would need

  1. Combinator scope. spread, stack and the other operator combinators should pass their scope to a chart() child, as layer does. One line; it is a bug fix more than a design change.
  2. Independent child scales. Children that read different fields need their own domains (parallel coordinates). This is the one real gap, and it touches the axis rules (#1032 chrome at chart boundaries).
  3. Ribbon identity by default. A ribbon over a record-shaped combinator joins ends that came from the same datum, so .layer(ribbon()) works without the explicit selectAll + group tier.
  4. Python and the wire. Object identity does not survive serialization: a columnar Python or IR version copies rows. There the join needs a row or link id after all, so unpivot's id comes back in another form.
  5. Bugs found: a by function receives the ref rather than the row (contradicting the projectBy doc comment), so group({ by: r => r }) silently draws nothing; a "depth" axis appears despite axes: false in the .layer form; the stack scale bug again.
  6. Ribbons can run backwards. selectAll lists nodes in the order their layout finished, not document order, and a two-end ribbon always runs from its first end's right edge to its second end's left edge. 28 of the energy sankey's 68 ribbons run backwards; painting hides it. Fix: document-order selectAll, or ribbons that use facing edges whatever the order.
  7. Ends need a spelling in the tree. A parent-to-child ribbon needs a sub-interval of the parent's edge per child. Either the ribbon allocates it (Approach A's size) or the box declares its ends.

Round 1 vs round 2

Round 1: ends are rows Round 2: syntax follows the data
Data you start from reshaped long (unpivot) as it is: wide rows, or d3's nodes + links (plus a nest join)
Ribbon identity an id column, ribbon({ by }) same datum, same ribbon (an id again in Python)
Per-axis types and scales lost: one mixed category column kept, once child scales exist
New core unpivot, ribbon({ by, at }) combinator scope, child scales, ribbon default, cols, nested child data, at
Parallel coordinates no (mixed types) yes, once child scales exist
Chord yes, with at same (each group is a list of matrix cells)

My read: round 2 is the better match for what users have (wide tables, d3-style node and link lists) and keeps types on fields, which round 1 cannot. Its cost is three core pieces, of which independent child scales is the only real design work. Round 1's unpivot stays as the converter for data that arrives in the other shape. I'd pick round 2 if you're comfortable with expression expansion in child lists. Otherwise, round 2 with the explicit .map still works today.

Why B

  • It desugars into the existing core (principles, "Why keep the core small"). Three of four hard examples needed no core change. The fourth, chords, needs parts, which labels need too.
  • One concept, one operator (api-design, "Operators and marks"). Span allocation is stack; A and C add a second stacker unless defined by rewrite.
  • Data flows as lists. An end is a row, like ggalluvial's lodes form and circlize's "row order is slot order".
  • It realizes #745. Ribbons stay one-to-one per row; the per-edge span allocation turned out to be the flow's stack.
  • Names from precedent. unpivot from polars, by the family key, at and part names from the label proposal. Same shape in JS and Python.

What would change the pick to A: ribbons over nodes placed by something other than the flow (gotree trees, node-link diagrams, flow maps) becoming a priority, or crossing-reducing end order proving impossible to state as a data sort. A can later be added as sugar defined by rewrite into B's pieces, so picking B does not close it off.

Out of scope: sankey node layout (column assignment, in-column relaxation; #701, #631) and fill-the-height gaps (#1165). Both showed up in the energy prototype; neither is about divided ends.

Decisions for you

  1. Is "ends are rows" the model, with span allocation done by the flow's stack (B), rather than by the ribbon (A)?
  2. Bring by back on ribbon and line as the ribbon's identity (ribbon({ by: "link" })), with travel order from the outermost tier?
  3. unpivot({ on, variable, value, id }) inside derive: keep the polars name, and create the row id in the same call rather than a separate withRowIndex step?
  4. End order: ship with a user sort key (a declared shortcut) and add a far-end order strategy later? Default per node (alluvium) or per side of each gap (flow)?
  5. ribbon({ at: "bottom" }) with the label proposal's part names, plus the rule that a ribbon leaves each end along that part's outward normal in screen space?
  6. Slack when in-sum and out-sum differ: default alignment start (as d3) or middle?
  7. Keep sankey node layout (columns, in-column order, fill-the-height gaps) out of this design, as separate issues?
  8. A tree-ends helper for sankey trees: here, or with #738?
  9. Round 2: make "syntax follows the data" the primary spelling (a record becomes direct-style children, a list becomes a flow), keeping unpivot only as a converter?
  10. Expression expansion: may a combinator child that mentions cols([...]) stand for one child per column, as polars expands pl.col([...])?
  11. Nested child data: chart(field("in")) (or unnest) for a parent's list field, plus a nestJoin helper to build it from flat tables?
  12. Independent child scales: should direct-style children that read different fields get their own domains by default, or by an explicit option?

Bugs found while prototyping

  1. A data-sized stack under two spreads gets its own scale per column when columns have different child counts (workaround: spread({ spacing: 0 })).
  2. A y spread orders groups top-down; a y stack orders them bottom-up.
  3. filter over a refs bag sees ref.datum as a bag, so r.datum.depth is undefined and everything is silently dropped.
  4. In polar, spread with spacing stops near 225° instead of closing the circle.
  5. chart(..., { legend: false }) on a non-root layer is ignored.
  6. The polar bake treats only connect and tween as relational leaves (a hard-coded type list).
  7. resolveGroupPaint resolves fill: "<field>" only for registered types.
