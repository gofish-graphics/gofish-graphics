Stacked and divided ribbons

A sankey is a stacked area chart whose stacks are nodes. Each ribbon end is a data row, the ends stack inside their node with the ordinary stack operator, and the ribbon stays one-to-one.

  1. Prototypes drew parallel sets, a sankey tree, and the full 48-node energy sankey with no core change, using today's stack, spread and ribbon.
  2. What is missing is small: a unpivot data helper, ribbon({ by }) to name which rows form one ribbon, and, for chord diagrams, ribbon({ at }) to say which part of a node each end attaches to.
  3. The runner-up has the ribbon allocate its own ends on nodes placed by anything: ribbon({ from, to, size }). It wins if ribbons over independently placed nodes become a priority.
Recommendation: Approach B, ends are rows. Span allocation is the flow's stack, so it desugars into the existing core, keeps one stacking mechanism, and realizes the direction recorded in #745: ribbons one-to-one per row, plus per-edge span allocation.

Terms

Node
A bar or arc whose length shows a total: a sankey node, a parallel-sets category, a chord group.
Link
One flow between two nodes, with a value.
End
The interval where one link meets one node. ggalluvial calls it a lode, d3-chord a subgroup, ELK and Graphviz a port.
Path
The chain of ends one ribbon threads: two for a sankey link, one per axis for a parallel-sets cohort.
Part
A named piece of a mark's outline that the mark declares: a rect's top, right, bottom, left. The coordinate transform carries parts along, so a polar rect's bottom is its inner arc. Same word as in the label proposal.
Unpivot
Turn columns into rows: a row with source and target becomes two rows with a side column. The polars name; dplyr says pivot_longer.

Your questions, answered

From the notes Answer
Extend the existing ribbon API? Yes, by two options: by (which rows form one ribbon) and at (which part each end attaches to). The span allocation itself does not live on the ribbon.
The stack operator, or a method like ribbon().stack()? The stack operator, applied to the ends inside each node. ribbon().stack() is Approach C below: it would be a second route to stacking next to the flow's stack, which matches the #290 note that a mark-side stack on a connector can only respell a row stack.
What do enclose, line, cut and labels contribute? line: the same ends give parallel coordinates and stringlines. enclose: draws a node box when in-sum and out-sum differ (Shape.box(), padding 0). cut: another way to make ends when the node is one drawn shape such as an image; for a rect it equals stacking the ends. labels: node labels are .label() on the node tier, ribbon labels are Place.along, and at reuses the label proposal's part names.
One-to-many, many-to-many? Ribbons stay one-to-one per link. Splits and merges come from several ends stacking in one node. The energy sankey (69 links, splits and merges) renders this way.

Today

A ribbon spans the full facing edge of each operand's box. No option attaches it to part of an edge, so every divided-end example builds one node per end and lists ribbons by name. The gallery Sankey Tree is about 137 lines for this reason.

Prior work

Every system that draws sankeys correctly stacks link values inside each node and then joins two intervals. The one general grammar without ends, Mascot, attaches every link at its node's middle and gets a thick-edged node-link diagram instead.

d3-sankey

One layout computes columns, node y, and each link's y0/y1 on both edges.

ggalluvial

ggforce

make_long gives one row per edge. Sankey and alluvial differ only by gap and baseline.

circlize / d3-chord

Sectors sized by total; links stacked in sectors. d3's ribbon() joins two angle intervals through the center.

Mascot (foil)

No end concept: every link leaves its node's middle, so widths pile up instead of tiling the edge. 

sourceAnchor: ["right", "middle"]
encode(link, "strokeWidth", "value")

Also surveyed: TikZ sankey (\sankeyfork{a}{25/b,10/c} divides a cross-section into sub-intervals that must sum to the parent, the closest model to this proposal), the Kibana Vega sankey (stack + lookup + linkpath, with node and slot stacks kept in sync only by a shared sort key), ELK port constraints (a ladder of who owns end order), Plotly, Highcharts, ECharts, networkD3, RAWGraphs, Kosara's Parallel Sets. Fixed chart types such as geom_sankey and go.Sankey are foils: they list arrangements instead of composing them.

Energy sankey: many-to-many, 48 nodes, 69 links

Proposed
chart(links)   // { source, target, value } + precomputed depth and order
  .flow(
    derive(unpivot({ on: ["source", "target"],
                     variable: "side", value: "node", id: "link" })),
    spread({ by: field("depth").sort(), dir: "x", spacing: 100 }),
    spread({ by: field("node").sort(order), dir: "y", spacing: 10 }),
    spread({ by: field("side").sort(["target", "source"]),
             dir: "x", spacing: 0 }),          // in-ends left, out-ends right
    stack({ by: field("key").sort(), dir: "y" }) // far node's rank
  )
  .mark(rect({ w: 6, h: "value", fill: "#555" }))
  .layer(ribbon({ by: "link", opacity: 0.4, fill: "source" }))

A node is its two end stacks side by side, so its height is the larger of its in-sum and out-sum. The side spread's alignment places the slack (TikZ's left/center/right anchor). enclose({ shape: Shape.box(), padding: 0 }) over each node's ends draws a box.

Each matrix cell is already an end. at: "bottom" attaches both ends to their inner arc. The band leaves each end along that part's outward normal, in screen space. The same rule describes today's sankey bezier (out of right along +x, into left along −x), so chords need no new curve. In Cartesian coordinates it gives thick arc-diagram bands.

How B composes

Desugars into

  • unpivot is a derive data helper.
  • by, at are ribbon options.
  • Span allocation is stack. Node and ribbon share one scale by construction, since the ends are the node.
  • Polar works once at exists.
  • line({ by }) over the same ends gives parallel coordinates.

Overlap check

  • stack: exact composition; the end stack is a stack.
  • cut: degenerate; for a rect node, cutting by link values equals stacking ends. Cut stays the tool for an image node.
  • enclose: none; it draws node boxes.
  • #786 default split: by overrides it only when named.

Trade-offs

  • Easy: no new layout; cohort identity across axes is free; chords and sankeys share one spec shape.
  • Awkward: users think of ends as rows; end order needs a sort key that agrees with the far node; ribbons cannot attach to nodes the flow did not lay out.
  • New terms: unpivot, by, at, all existing words.

Approach A: the ribbon allocates its own ends

Runner-upNodes table and links table, the d3-sankey inputs. Nodes come from any chart; the ribbon's size divides each node's facing part. 
layer([
  chart(nodes)
    .flow(spread({ by: "depth", dir: "x", spacing: 100 }),
          spread({ by: "name", dir: "y", spacing: 10 }))
    .mark(rect({ w: 12, h: "value" }).name("nodes")),
  chart(links)
    .flow(resolve(["source", "target"], { from: selectAll("nodes") }))
    .mark(ribbon({ from: "source", to: "target", size: "value", opacity: 0.5 })),
])
layer([
    chart(nodes).flow(spread(by="depth", dir="x", spacing=100),
                      spread(by="name", dir="y", spacing=10))
        .mark(rect(w=12, h="value").name("nodes")),
    chart(links).flow(resolve(["source", "target"], from_=select_all("nodes")))
        .mark(ribbon(from_="source", to="target", size="value", opacity=0.5)),
])

Desugars into a fresh stack of ends per (node, part), placed with relate() and Constraint.align span, then one-to-one ribbons. End order is a sort after the nodes are placed, by the far end's position. New: a data channel on a connector that must share the node's scale (same measure), a post-layout sort, a loud error when ribbon sizes exceed the node, and at.

Easy

  • d3-shaped data as-is.
  • Nodes from any layout: gotree, scatter, a map.
  • Exact crossing-reducing end order, no user sort key.

Awkward

  • Node value and ribbon sizes must agree.
  • A connector owns a data channel and a scale.
  • Parallel sets need one link per gap, losing cohort identity.

Overlap

  • Exact composition only if defined by the rewrite into relate + stack + ribbon. Otherwise a second stacking mechanism next to stack.

Approach C: ribbon().stack()

Not recommendedYour floated spelling, read as ggplot's position = "stack": ribbons that share a node stack their ends there. 
// sankey
chart(links)
  .flow(resolve(["source", "target"], { from: selectAll("nodes") }))
  .mark(ribbon({ from: "source", to: "target" }).stack({ size: "value" }))

// and stacked area would gain a second spelling
chart(rows).flow(scatter({ by: "year", x: "year" }))
  .mark(ribbon({ h: "value" }).stack({ by: "series" }))

Its sankey meaning is exactly A's, so C is A with a method spelling. It also gives stacked area a second route next to spread(x), stack(series), which is a large partial overlap with the flow's stack. By the calls, methods and options rule, a method reads its caller's state; this one reads every other ribbon at the same node, which is a set-level operation. No separate pictures: the outputs are A's and today's stacked area.

Why B

  • It desugars into the existing core (principles, "Why keep the core small"). Three of four hard examples needed no core change. The fourth, chords, needs parts, which labels need too.
  • One concept, one operator (api-design, "Operators and marks"). Span allocation is stack; A and C add a second stacker unless defined by rewrite.
  • Data flows as lists. An end is a row, like ggalluvial's lodes form and circlize's "row order is slot order".
  • It realizes #745. Ribbons stay one-to-one per row; the per-edge span allocation turned out to be the flow's stack.
  • Names from precedent. unpivot from polars, by the family key, at and part names from the label proposal. Same shape in JS and Python.

What would change the pick to A: ribbons over nodes placed by something other than the flow (gotree trees, node-link diagrams, flow maps) becoming a priority, or crossing-reducing end order proving impossible to state as a data sort. A can later be added as sugar defined by rewrite into B's pieces, so picking B does not close it off.

Out of scope: sankey node layout (column assignment, in-column relaxation; #701, #631) and fill-the-height gaps (#1165). Both showed up in the energy prototype; neither is about divided ends.

Decisions for you

  1. Is "ends are rows" the model, with span allocation done by the flow's stack (B), rather than by the ribbon (A)?
  2. Bring by back on ribbon and line as the ribbon's identity (ribbon({ by: "link" })), with travel order from the outermost tier?
  3. unpivot({ on, variable, value, id }) inside derive: keep the polars name, and create the row id in the same call rather than a separate withRowIndex step?
  4. End order: ship with a user sort key (a declared shortcut) and add a far-end order strategy later? Default per node (alluvium) or per side of each gap (flow)?
  5. ribbon({ at: "bottom" }) with the label proposal's part names, plus the rule that a ribbon leaves each end along that part's outward normal in screen space?
  6. Slack when in-sum and out-sum differ: default alignment start (as d3) or middle?
  7. Keep sankey node layout (columns, in-column order, fill-the-height gaps) out of this design, as separate issues?
  8. A tree-ends helper for sankey trees: here, or with #738?

Syntax to review

New spelling Meaning
derive(unpivot({ on, variable, value, id }))
unpivot(on=..., variable=..., value=..., id=...) 		Columns to rows, keeping a row id that names the path or link.
ribbon({ by }), line({ by }) Rows that share the key form one ribbon. Removed in #786; returns with this narrower meaning.

Bugs found while prototyping

  1. A data-sized stack under two spreads gets its own scale per column when columns have different child counts (workaround: spread({ spacing: 0 })).
  2. A y spread orders groups top-down; a y stack orders them bottom-up.
  3. filter over a refs bag sees ref.datum as a bag, so r.datum.depth is undefined and everything is silently dropped.
  4. In polar, spread with spacing stops near 225° instead of closing the circle.
  5. chart(..., { legend: false }) on a non-root layer is ignored.
  6. The polar bake treats only connect and tween as relational leaves (a hard-coded type list).
  7. resolveGroupPaint resolves fill: "<field>" only for registered types.
