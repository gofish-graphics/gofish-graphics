# Exposition sources

Use these sources as design references, not as a template to imitate mechanically.

- [How to Design Programs: Preface and design recipes](https://htdp.org/2024-11-6/Book/part_preface.html) — develop programs and explanations from explicit data definitions, examples, and systematic recipes.
- [Simon Peyton Jones, *How to Write a Great Research Paper*](https://www.microsoft.com/en-us/research/uploads/prod/2016/07/How-to-write-a-great-research-paper.pdf) — organize technical writing around a concrete problem and the reusable idea that solves it.
- [MIT, *Guidelines for Writing Mathematical Proofs*](https://web.mit.edu/mathp2/www/piil.html) — introduce notation deliberately and make proof structure readable.
- [Donald Knuth, Tracy Larrabee, and Paul Roberts, *Mathematical Writing*](https://cs-faculty.stanford.edu/~knuth/klr.html) — guidance on terminology, notation, sentence-level clarity, and mathematical presentation.
- [Robert Harper, *Practical Foundations for Programming Languages*](https://www.cs.cmu.edu/~rwh/pfpl/abbrev.pdf) and its [interpreter supplement](https://www.cs.cmu.edu/~rwh/pfpl/supplements/interpreters.pdf) — connect syntax, judgments, dynamics, and executable interpretations.
- [Barbara Liskov and Stephen Zilles, *Specification Techniques for Data Abstractions*](https://csg.csail.mit.edu/CSGArchives/memos/Memo-117.pdf) — describe abstractions through observable behavior and precise specifications.
- [Barbara Tversky, Julie Morrison, and Mireille Bétrancourt, *Animation: Can It Facilitate?*](https://www.tc.columbia.edu/faculty/bt2158/faculty-profile/files/_Morrison_Betrancourt_AnimationCanitfacilitate.pdf) — apply congruence and apprehension principles; animation should match the represented process and remain perceptually understandable.
- [Jill Larkin and Herbert Simon, *Why a Diagram Is (Sometimes) Worth Ten Thousand Words*](https://iiif.library.cmu.edu/file/Simon_box00014_fld00953_bdl0001_doc0001/Simon_box00014_fld00953_bdl0001_doc0001.pdf) — use diagrams when spatial grouping and local inference materially improve reasoning.
- [Google developer documentation, *Use consistent terminology*](https://developers.google.com/tech-writing/one/words) — choose one precise term for one concept and avoid casual synonym drift.
- [Rustdoc, *Documentation tests*](https://doc.rust-lang.org/rustdoc/documentation-tests.html) — keep explanatory code executable so examples and implementation cannot silently diverge.
- [Diátaxis](https://diataxis.fr/) — distinguish explanation from tutorials, how-to guides, and reference material while allowing them to link to one another.
- [Leslie Lamport, *How to Write a 21st Century Proof*](https://www.microsoft.com/en-us/research/publication/write-21st-century-proof/) — expose proof hierarchy and intermediate obligations instead of hiding them in dense prose.
